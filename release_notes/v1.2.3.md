# Recify v1.2.3 Release Notes

Status: release candidate
Audience: development / release management
Target release date: 2026-07-30
Last updated: 2026-07-30

## 概要

v1.2.3は、新しい利用者・管理者向け機能を追加せず、Active Storageの画像処理に関するセキュリティ問題へ対応するpatch releaseです。

公式Rails advisoryのCVE-2026-66066／GHSA-xr9x-r78c-5hrmに基づき、Rails framework componentsとActive Storageを8.1.3.1へ更新します。攻撃手順、悪用を再現する具体的な入力、production credentialはこのreleaseへ含めません。

破壊的変更、DB schema変更、保存済みデータの補正、公開機能の追加はありません。

## Security update

- Rails framework componentsを8.1.3.1へ統一
- Active Storageを修正版の8.1.3.1へ更新
- GemfileでRails 8.1.3.1をsecure floorとして固定
- vips processor、ruby-vips 2.2.1以上、libvips 8.13以上のruntime契約を回帰specで検証
- 通常の画像variant生成が修正版runtimeで成功することをsynthetic fixtureで検証
- GitHub Actionsのtest jobでlibvipsを明示的に導入し、versionを確認

Recifyは信頼できない利用者入力として画像uploadを受け付け、Active Storageのvips processorを使用するため、修正前の8.1.3は公式advisoryの影響条件に該当します。この実装・検証作業では、productionにおける侵害有無の調査やsecret rotationを実施していません。

## Compatibility

- v1.2.2の公開互換性契約を維持
- Ruby 4.0.5を維持
- route、公開入出力形式、認証・認可、upload形式と上限、画像削除方針を変更しない
- Active Storage signed URLと添付の既存契約を変更しない
- 新しい必須環境変数なし
- DB migration、schema変更、保存済みデータのbackfillなし
- OCR／AI provider契約と外部API呼び出しを変更しない

## Runtime verification

2026-07-30に、production Dockerfileから`--pull --no-cache`でlinux/amd64 imageを作成し、次を確認しました。

- base image: `ruby:4.0.5-slim`
- image内libvips: `8.16.1`
- ruby-vips: `2.3.0`
- production-mode boot: Rails／Active Storage `8.1.3.1`
- production-mode safe image variant smoke: passed

base image tagとDebian packageはmutableであり、将来のbuildで同一artifactを完全には再現できないriskがあります。今回のhotfixでは、production imageへ検証専用packageを追加せず、根拠のないbase image pinningも行いません。CIではruntime要件を実測するため、test jobだけにlibvipsのcommand-line toolsを導入します。main統合後にbuildするdeploy対象のexact imageでも、version、boot、variant smokeを再確認します。

## Database migration

- v1.2.2からv1.2.3への新規migrationなし
- schema変更なし
- migration rollbackなし
- deploy時は通常のentrypointによる`db:prepare`とpending migrationなしを確認

## Deployment notes

- hotfix branchからmain向けPull Requestを作成し、required checksとreview完了後にCreate a merge commitで統合
- mainのhotfix merge commitへannotated tag `v1.2.3`を作成
- tag targetと同じexact SHAをdeploy
- production image内のActive Storage、ruby-vips、libvips versionとproduction bootをdeploy前に再確認
- deploy後にupload、画像表示、画像解析、削除、認証・認可をsynthetic dataでsmoke確認
- external OCR／AI provider callは、別途承認された確認以外では実行しない
- smoke後にmainをdevelopおよびactive release branchへPull Requestでback-merge

## Potential exposure response

公式advisoryは、影響対象applicationのprocessから読み取れるsecretをpotential exposureとして扱い、修正版deploy後に変更することを推奨しています。

このrelease candidateではsecret rotationを実施していません。rotationは、owner、切替順、session・signed URLへの影響、rollback不能点、validation方法を確定した別の明示承認下で行います。特にRails signing secretの変更は、既存session、signed cookie、signed ID、Active Storage URLを無効化するため、修正版deploy後の計画cutoverが必要です。

変更前のsecretはfallbackとして保持せず、切替後の不具合は新しいsecretの再発行を含むforward recoveryで扱います。

実値、内部保存先、production credential、raw provider dataはGit、Pull Request、release reportへ記録しません。

## Temporary mitigation

- 新しいkill switchは追加しない
- ブラウザからstorageへ直接送信するupload経路は既存どおり有効化しない
- OCR停止は新規Receipt画像解析を減らせるが、すべての画像upload入口を閉じる手段ではない
- 完全なHTTP遮断が必要な根拠がある場合は、既存maintenance手順を別承認で使用
- Cloudflare ruleやproduction settingを、このhotfix実装作業では変更しない

## Rollback notes

- DB migrationとschema rollbackは不要
- Active Storageを8.1.3へ戻すapplication rollbackは既知のsecurity issueを再導入するため、通常のrollback手段として使用しない
- deploy後に問題が見つかった場合は、maintenance等で画像処理経路を露出低減し、v1.2.3からのforward-fixを優先
- 公開済みtagを移動、削除、上書きしない
- secret rotation実施後は、旧secretへ戻すと新しいsessionやsigned URLが失効し得るため、rotation固有のrollback計画に従う
