# Recify v1.2.2 Release Notes

Status: release candidate
Audience: development / release management
Target release date: 2026-07-20
Last updated: 2026-07-20

## 概要

v1.2.2は、新しい利用者向け機能を追加せず、コマンド形式の定期処理を実行するworker coverageを回復するpatch releaseです。

v1.2.1のannotated tagと公開済み履歴は維持しますが、production preflightでqueue blockerが見つかったため、v1.2.1はproductionへdeployしていません。productionはv1.0.0からv1.2.2へ直接更新し、v1.1.0からv1.2.1までの累積変更も同時に反映します。v1.2.2は、v1.2.1を置き換えるproduction releaseです。

破壊的変更、新しい利用者・管理者向け機能、保存済みデータの自動補正はありません。

## Solid Queue定期処理

- queueを明示しないコマンド形式の定期処理が使用する`solid_queue_recurring`を、専用workerで処理
- 専用workerを`1 process`、`1 thread`、`polling_interval: 1`とし、通常jobと分離して直列実行
- recurring scheduleの実効queueとworker selectorをproduction validatorで照合
- exact、全queue、prefix selectorと、class形式の定期処理が解決するqueueを検証
- queue名のtypoやschedule変更によってworker coverageが失われた場合、release前の検証で失敗
- `default`、`receipt_ocr`、`receipt_ai`、`receipt_finalize`の既存worker構成を維持
- 定期cleanupのschedule、command、削除対象、job class、serialized argumentsは変更なし

定期cleanupは、Solid Queue内の保持期間を過ぎた完了済みjobだけを既存のbatch単位で削除します。ready、claimed、scheduled、failedのjob、primary DBのreceipt、外部API、メールには作用しません。

## Compatibility

- v1.2.1の公開互換性契約を維持
- route、公開入出力形式、保存済みデータの意味、Active Job class名とserialized argumentsの変更なし
- 新しい必須環境変数、direct dependency、利用者向け設定なし
- operatorによる必須config変更なし。repositoryのqueue構成へ専用workerを追加
- v1.2.1からv1.2.2への新規DB migrationなし
- v1.2.1 tagを移動、削除、上書きせず、v1.2.2を前進patchとして追加
- 破壊的変更なし

## Production deployment scope

- release差分は`v1.2.1..v1.2.2`
- production差分は`v1.0.0..v1.2.2`
- v1.1.0、v1.2.0、v1.2.1の累積変更は各版のrelease notesを参照
- v1.2.1をproductionへdeployせず、v1.2.2だけをmainからdeploy
- production preflight、main exact SHA CI、annotated tag作成、migration、deploy、queue drain、smokeの順で実施

## Database migration

- v1.2.1からv1.2.2への新規migrationはなし
- production v1.0.0からの累積更新では、`20260710103002_add_lock_version_to_receipts`を適用
- `receipts.lock_version`は`integer`、`NOT NULL`、default `0`の追加列
- 新applicationへtrafficを切り替える前に、container entrypointの`db:prepare`が成功したことを確認
- migration後にpending migrationがないこと、schemaが期待定義と一致することを確認
- 既存receiptの総件数、`lock_version`がNULLの件数、最小値、最大値、初期値件数を集計だけで確認
- 手動`ALTER`、既存production DBへのschema load、保存済みreceiptの再生成、Amountデータのbackfillや自動修復は行わない

## Queue backlog drain

- historical ready backlogを直接削除、discard、table更新せず、専用workerの通常のclaim / performで処理
- 初期drainでもprocess数とthread数を増やさず、直列実行を維持
- ready、claimed、failed、oldest ready age、worker heartbeat、CPU、memory、DB connection、DB lock、request latency、5xx、Sentryを監視
- failed増加、lock待ち、resource悪化、重複実行、5xxを確認した場合はworkerをclean stopし、queue recordを残したまま原因を確認
- 旧backlogの消費、oldest ready ageの定常化、新しい毎時jobの通常消費、failed増加なしをdrain完了条件とする
- drain中のapplication再deployやworker再起動を避ける

historical failed executionはready backlogのdrain対象外です。対象blobとstorage fileが既に存在しない`ActiveStorage::AnalyzeJob`は、同じ入力で再試行しても成功しないため、本releaseでは一括retry、discard、deleteを行わず、履歴として保持します。

## Complete recovery set

production preflightでは、次を同じmaintenance windowの完全なrecovery setとして作成・検証します。

- primary、queue、cable、cacheの4 DB
- ActiveStorage
- application secret recovery materialとActive Record Encryption material
- production SHA、VERSION、migration state、deploy構成の復旧情報
- 各artifactのsize、checksum、archiveまたはdump integrity
- 暗号化済みoff-host copy、access制限、24時間RPO、restore proof

secret、内部保存先、hostname、record ID、PIIはGit、PR、共有ログ、release reportへ出力しません。完全性またはrestore可能性を確認できない場合はNo-Goとします。

## Deployment notes

- production preflightで完全なrecovery set、synthetic smoke data、queue状態、failed execution分類、migration互換性を確認
- 新しい環境変数や手動のqueue routing設定は不要
- main向けPRとmain exact SHA CIがgreenになった後、同一SHAへannotated tagを作成
- canonical Kamal手順でmainのtag targetをdeploy
- new containerのentrypointで`db:prepare`を完了してからhealth checkとproxy切替を行う
- web、通常worker、`solid_queue_recurring`専用worker、queue heartbeat、Cloudflare経路、origin healthを確認
- deploy後にready backlogを削除せずdrainし、application負荷とfailure増加を監視
- production Amountデータの自動監査・自動修復は行わない

## Synthetic smoke

- 実利用者のaccountやreceiptを使用しない
- credentialをGit、PR、ログへ保存しない
- 承認済みのguestまたはsynthetic accountを使用
- 架空の店舗・商品と単純な金額を持つ画像なしのmanual receiptをmigration前に作成
- OCR / AI providerの有料呼び出しを行わない
- deploy後に同じreceiptで`lock_version`初期値、編集保存、version増加、再保存を確認
- 数量の往復、Amount previewと保存、flash / toast、Turbo、通常のActionCable経路を確認
- UIからreceiptとsynthetic accountを個別に削除し、runnerによる一括補正を行わない
- UI cleanupに失敗した場合は推測で補正せず停止

## Rollback notes

- queue worker追加そのものにDB schema rollbackは不要
- application rollbackで`receipts.lock_version`列を自動削除しない
- migration rollbackは、完全なrecovery setと互換性を確認した承認済み手順がない限り実施しない
- backlog drain中にrollbackや再deployを行わず、先にworkerをclean stopしてqueue状態を保存
- failed executionをrollback前後で一括retry、discard、deleteしない
- v1.2.1 tagやmain履歴を書き換えず、可能な場合は後続patchによるforward-fixを優先
